# Développement et déploiement

Transport SMTP : variables disponibles `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `EMAIL_USE_SSL` et `EMAIL_TIMEOUT` (10 secondes par opération par défaut). Pour STARTTLS, activer TLS et désactiver SSL ; pour TLS implicite, l’inverse. Un timeout nul, négatif ou non fini et TLS/SSL simultanés sont refusés au chargement. Aucun changement du `.env` local n’est nécessaire. Contrat, retours API et limites de reprise : `mail-delivery.md`. La validation sur le fournisseur réel reste à réaliser sur la cible de déploiement ; ne jamais désactiver la vérification du certificat pour contourner une panne.

Notifications : synchronisation personnelle depuis l’application à l’ouverture puis toutes les 60 secondes lorsque la cloche est active. Pour une exploitation planifiée, la commande `python manage.py sync_notifications` synchronise les adhésions actives autorisées, ou une société avec `--company UUID`. Elle ne transmet aucun e-mail. Aucune tâche système/cron n’a été créée dans cet environnement ; planification et fréquence à configurer lors du déploiement selon la charge. Le module Dashboard doit être activé explicitement par société, ses permissions et celles des modules sources restent nécessaires.

Export PDF : ReportLab et ses polices embarquées sont installés via `backend/requirements.txt`, versions contraintes dans `requirements.lock.txt`. Aucun navigateur, accès réseau ou fichier public n’est requis pour générer un document. Tests de texte avec pypdf ; pour la QA visuelle Windows sans Poppler, installer séparément `backend/requirements-qa.txt` (PDFium), rendre les fixtures ignorées de `.local/pdf-qa` et les inspecter. Ces dépendances et le rendu sont vérifiés localement ; l’image Docker complète reste à exécuter lors du jalon exploitation.

Copier `.env.example` en `.env` localement, fournir des secrets uniques. Le code Python lit l’environnement du processus ; Compose charge `.env` et le script `infrastructure/backend.ps1` le charge pour Windows. Ne pas activer DEBUG en production.

Avec Docker : `docker compose up --build`. Le frontend est accessible sur http://localhost:5173, API via proxy même origine. PostgreSQL n’est publié que sur 127.0.0.1 pour le développement, pas sur une interface publique. Données persistées dans un volume nommé. Les migrations sont une commande explicite : `docker compose run --rm backend python manage.py migrate` avant le démarrage du backend.

Sans Docker : installer PostgreSQL 17, créer une base et un rôle dédiés, installer requirements.lock.txt dans .venv, configurer .env. Exécuter `./infrastructure/backend.ps1 migrate`, puis `./infrastructure/backend.ps1 runserver`. Dans frontend : `npm ci`, `npm run dev`.

L’e-mail de développement est enregistré dans `.local/emails` (fichiers privés ignorés par Git), avec le backend Django filebased de `.env.example`. Ouvrir le fichier le plus récent et son lien, puis cliquer sur « Vérifier mon adresse ». Aucun message n’est réellement envoyé à une boîte personnelle avec ce transport. Ne jamais servir ce dossier par HTTP ni le placer dans les fichiers statiques. Sous Docker, le chemin par défaut est interne au conteneur : configurer un SMTP de test accessible ou un volume privé avant un parcours de vérification. En production, configurer le SMTP réel et le backend SMTP.

Pour un compte local déjà inscrit dont le lien de console a été perdu : `./infrastructure/backend.ps1 resend_verification adresse@example.com`. Le compte reste non vérifié jusqu’à l’utilisation du nouveau lien. Les anciens transports console restent pris en charge et sont annoncés correctement par l’interface. Redémarrer Django après modification de `.env`.

État temporaire demandé par l’utilisateur : le `.env` de ce poste contient `REQUIRE_EMAIL_VERIFICATION=0`. Avec `DJANGO_DEBUG=1`, on peut se connecter directement, y compris avec les comptes non vérifiés existants, et créer son entreprise. Aucun e-mail de vérification n’est envoyé à l’inscription dans ce mode. Pour réactiver le parcours ultérieurement, mettre `REQUIRE_EMAIL_VERIFICATION=1` et redémarrer Django. Les fichiers et jetons existants sont conservés. L’option ne désactive pas la vérification lorsque DEBUG vaut 0.

Compose est un environnement local, pas une configuration de production finalisée. Avant production : terminaison HTTPS, hôtes autorisés explicites, SMTP réel, secrets, paramètres cookies/CSRF, sauvegardes PostgreSQL et restauration testée, contrôle de santé, collecte des logs sans corps sensibles, médias privés et procédure de migration. Ne pas faire confiance à des en-têtes proxy issus d’une connexion publique. Le jeton de vérification figure dans le fragment du lien (jamais envoyé dans une URL HTTP) puis dans le corps POST, afin de ne pas apparaître dans les journaux d’accès.
# Stockage privé des logos et accès plateforme

Exploitation locale vérifiée : `./infrastructure/backend.ps1 healthcheck`, `backup_instance`, puis `restore_instance DOSSIER` (nouvelle cible uniquement). PostgreSQL 17.12 disponible sur ce poste ; sauvegardes et clones privés sous `.local`, inclus dans les exclusions Git/Docker. Démonstration de restauration réelle et résultats dans progress.md ; procédure, limites et confidentialité dans operations.md. Le backend Compose dispose d’un healthcheck PostgreSQL/migrations ; le volume médias est initialisé au propriétaire applicatif dans l’image. Docker/HTTPS et stockage distant restent non validés dans cet environnement.

Configurer MEDIA_ROOT sur un stockage persistant privé accessible au seul backend. Local : `.local/media` ignoré Git ; Compose : volume `company_media` monté sous `/app/private-media`. Nginx relaie les routes API privées, limite le corps à 3 Mio et n’expose aucun répertoire média. Sauvegarder les médias avec PostgreSQL ; ne supprimer ni le volume ni les anciennes versions sans décision explicite. Configuration Compose préparée, à vérifier dans un environnement Docker disponible.

Attribution opérateur : `./infrastructure/backend.ps1 grant_platform_admin ADRESSE_EXISTANTE` sous Windows. Compte actif existant et politique de vérification e-mail respectée ; aucun mot de passe ou compte par défaut créé. Ouvrir `/plateforme` après actualisation de la session frontend. La commande est idempotente et journalise la première attribution. Les privilèges plateforme ne donnent aucun droit sur les routes métier d’une entreprise sans adhésion et permission.
